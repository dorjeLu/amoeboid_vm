= amoeboid: operator guide
:toc: left
:toclevels: 2
:icons: font
:source-highlighter: rouge

amoeboid runs coding agents inside throwaway-feeling but persistent NixOS microVMs.
You pick which host directories a VM may see (each read-write or read-only); everything else on your machine stays out of reach.
Each VM has a name, a persistent home directory, ssh on a loopback port, and its own copy of the NixOS configuration it is built from.

This guide is for the person running VMs. Everything an agent inside a VM needs to know is in `~/amoeboid/README.md` inside the VM.

== Install

Requirements:

* Linux x86_64 with KVM: `/dev/kvm` readable and writable by your user.
* Nix with the daemon running. amoeboid enables `nix-command` and `flakes` for its own calls; no `nix.conf` change needed.
* OpenSSH client tools (`ssh`, `ssh-keygen`).
* mise, or Python 3.14 and uv.

From the checkout:

[source,fish]
----
mise install          # python 3.14 + uv, as pinned in mise.toml
mise run install      # = uv tool install --editable --force .
amoeboid --help
----

The install is editable: it runs the checkout, so `git pull` updates it.
Alternatively symlink `amoeboid.py` from the checkout into your `$PATH`; it re-runs itself through `uv run`.

Nothing else is installed on the host: qemu, virtiofsd and the guest system are built into `/nix/store`.

== First run

The first `amoeboid` command that needs configuration creates, using the account you run it as:

`~/.config/amoeboid/run_config.kdl`:: amoeboid's settings (<<config>>).
`~/.config/amoeboid/host_<user>.nix`:: your user name, uid and gid for the guest, plus any per-machine NixOS settings. Rendered once, never overwritten; yours to edit.
`~/.config/amoeboid/nix_presets/default/`:: a copy of the NixOS configuration bundled with amoeboid, which new VMs are created from (<<presets>>).

`amoeboid --help` prints the resolved locations of all of these for you.
`amoeboid config` prints the configuration; `amoeboid presets` lists presets.

== Running a VM

[source,fish]
----
# foreground: the VM's serial console takes over the terminal
amoeboid start ~/dev/app ~/dev/libs:ro

# background: shows the boot log until ssh works, then returns
amoeboid start --detach --name proj ~/dev/app
amoeboid ssh --name proj
amoeboid ssh --name proj -- cargo test     # run a command
amoeboid stop --name proj
----

=== Names are identities

A VM is identified by its name (`--name`, default `default`; letters, digits and `-`).
The name selects its persistent home, its configuration, its pinned ssh host key and its hostname.
Running `start` with a name again resumes that VM: a fresh boot into the same home (there are no RAM snapshots).
Different names run side by side; one instance per name.

=== Choosing what to share

Each `MOUNT` is `PATH[:rw|:ro]` (default `rw`). A directory appears inside the VM at the same absolute path.

* Read-only (`:ro`) is enforced on the host: even root in the VM cannot write there.
* Read-write means an agent can change or delete anything in that directory. Share the narrowest directories that work.
* `/`, `/home`, your home and the guest's home are refused, since they would hide the VM's own home. Nested shares are fine; a directory may be given once.

Without any `MOUNT`, amoeboid uses, in order: what that VM shared last time (recorded on the host), `default-mounts` from the config, or asks interactively (and offers to save the answer as `default-mounts`).
`--save-mounts` stores the given mounts as `default-mounts`.

=== Foreground or detached

Foreground (default):: the serial console is your terminal until the guest powers off. Leave with `poweroff` inside the VM, or `amoeboid stop` from another terminal.
`--detach`:: the boot log is streamed until the guest's sshd answers (`--boot-timeout`, default 180 s), then amoeboid prints how to connect and exits. The console keeps going to `~/.local/share/amoeboid/NAME/console.log`.

Either way, the ssh port and connect command are printed before boot.

=== Day-to-day commands

[cols="1,3"]
|===
|`amoeboid list` |every VM, whether it runs, its ssh port and its shares
|`amoeboid ssh [--name N] [-- ARGS]` |shell or command in a running VM; `ARGS` go to ssh after the destination
|`amoeboid stop [--name N] [--timeout S]` |ACPI power-off, wait (default 60 s), then kill qemu if needed
|`amoeboid restart [--name N] [MOUNT ...]` |stop, then start detached and rebuilt; keeps the last shares unless given new ones
|`amoeboid presets` |list presets and which one new VMs use
|`amoeboid config [--path]` |print the configuration file (or its location)
|===

Every command has `--help`. Options are long-only and must be spelled out in full.

=== Inside the VM

You are logged in (console) or connect (ssh) as your own user name, with your uid/gid, passwordless `sudo`, and fish with mise.
The home directory persists across restarts; everything outside it and the shares is reset on every boot.
The default configuration includes opencode, mise (prebuilt node/python), rustup, a C toolchain, python3, nodejs, ripgrep, fd, jq, yq, git, gh and the usual network, archive and process tools.

Agents can search packages with `nixpkgs-search REGEX` but cannot install through Nix: the VM's `/nix/store` is your host store, shared read-only. User-level installs into the home (mise, rustup, `pip --user`, `npm -g`, downloaded binaries) do work and persist.

First-time setup per VM, e.g. `opencode auth login` or `rustup default stable`, persists in that VM's home.

== NixOS configurations

=== Where configuration lives

----
amoeboid's bundled nix/  ──first run──▶  ~/.config/amoeboid/nix_presets/default/
nix_presets/<preset>/    ──new VM─────▶  ~/.local/share/amoeboid/NAME/nix/   ◀── what is built
NAME/nix/                ──new VM─────▶  ~/amoeboid/nix/        in the VM    (the VM's own copy)
NAME/nix/ + host module  ──each start─▶  ~/amoeboid/reference/  in the VM    (what is running)
----

A configuration is a directory holding a small flake:

[cols="1,3"]
|===
|`flake.nix`, `flake.lock` |pins nixpkgs and microvm.nix; takes your host module as its `host` input
|`base.nix` |plumbing amoeboid relies on: user, shares, networking, ssh, console
|`recipe.nix` |what is in the VM: packages, services, vcpu/memory, tweaks
|`host-default.nix` |placeholder for the `host` input (amoeboid always overrides it)
|===

=== Presets

Presets are directories under `~/.config/amoeboid/nix_presets/`. To make one:

[source,fish]
----
cd ~/.config/amoeboid/nix_presets
cp -r default rust
$EDITOR rust/recipe.nix
amoeboid start --name crate --base-nix-config rust ~/dev/crate
----

`--base-nix-config` takes a preset name or any path to a directory with the same layout (`./my-config`, `~/configs/x`).
`base-nix-config` in the config file sets the preset new VMs use when the flag is absent.

`default` is never overwritten, so it doesn't pick up amoeboid's own updates to the bundled configuration. To refresh it, delete it; it is re-copied on the next run.

=== Changing a VM

A VM is created from a preset once; afterwards it builds its own copy in `~/.local/share/amoeboid/NAME/nix/`, and later preset edits don't affect it.

* *Edit that VM*: change `NAME/nix/recipe.nix` (or any file there), then `amoeboid restart --name NAME`.
* *Re-create it from a preset*: `amoeboid restart --name NAME --base-nix-config rust`, which replaces `NAME/nix/` (the VM's home is kept).
* *Update nixpkgs*: `nix flake update nixpkgs microvm` in `NAME/nix/` (or in a preset), then restart.

Rebuilds after small changes take seconds; unchanged configurations aren't rebuilt.

=== Adopting changes an agent made

Inside the VM, `~/amoeboid/nix/` is the agent's own full copy of the configuration (with your host module as `host.nix`), and `~/amoeboid/reference/` is what is actually running.
amoeboid never reads the agent's copy and never overwrites it, so its edits have no effect until you apply them.

On the host, the agent's copy is at `~/.local/share/amoeboid/NAME/guest/home/amoeboid/nix/`. To review and adopt:

[source,fish]
----
set vm ~/.local/share/amoeboid/proj
diff -ru $vm/nix $vm/guest/home/amoeboid/nix     # host.nix only exists on the guest side
cp $vm/guest/home/amoeboid/nix/recipe.nix $vm/nix/recipe.nix   # copy files, don't follow links
amoeboid restart --name proj
----

WARNING: The configuration is evaluated into the qemu runner, which runs on your machine as you. A recipe can add qemu arguments, extra shares or nixpkgs overlays that reach anything your user can. Read what you adopt; don't copy whole trees blindly.

== Configuration file

`~/.config/amoeboid/run_config.kdl` (KDL v2; `$XDG_CONFIG_HOME` is honoured):

[source,kdl]
----
user "alice"
uid 1000
gid 1000
base-nix-config "default"
(list)default-mounts {
    - {
        path "/home/alice/dev"
        mode "rw"
    }
}
(list)home-files {
    - ".gitconfig"
}
ssh {
    port 0
}
----

[cols="1,3"]
|===
|`user`, `uid`, `gid` |the guest account. Change the user here, not only in the host module: a new `host_<user>.nix` is rendered for a new name.
|`base-nix-config` |preset name or directory for new VMs
|`default-mounts` |shares for a new VM started without `MOUNT`s
|`home-files` |files under your home copied into each VM's home on every start (host copy wins). Seeded with your git config if you have one; a signing key or credential helper it references won't exist in the VM.
|`ssh.port` |host loopback port for ssh; `0` picks a free one per start
|===

amoeboid reads the file once per command. It rewrites it only when saving something itself (first run, `--save-mounts`, saving prompted mounts), atomically and in canonical form, keeping only the header comment.
Unknown keys or bad values stop amoeboid with every problem listed.

`host_<user>.nix` next to it is a NixOS module merged into every VM, e.g. for machine-wide sizing:

[source,nix]
----
{ ... }:
{
  amoeboid.user = "alice";
  amoeboid.uid = 1000;
  amoeboid.gid = 1000;
  microvm.vcpu = 4;
  microvm.mem = 4096; # MiB; avoid exactly 2048, qemu hangs
}
----

== Files on the host

[source]
----
~/.config/amoeboid/
├── run_config.kdl
├── host_<user>.nix
└── nix_presets/<preset>/

~/.local/share/amoeboid/NAME/          ($XDG_DATA_HOME)
├── nix/                     the VM's configuration (built every start)
├── vm -> /nix/store/...     last build: runner + virtiofsd (also a GC root)
├── mounts                   last run's shares
├── console.log              console of the last --detach boot
├── ssh/                     the VM's host key and the known_hosts pin
└── guest/                   shared into the VM at /mnt/amoeboid; the VM can write here
    ├── home/                the VM's home directory
    │   └── amoeboid/        nix/ (agent's copy), reference/, README.md
    └── mounts, hostname, term, ssh_host_ed25519_key   written by amoeboid each start

$XDG_RUNTIME_DIR/amoeboid/NAME/        (tmpfs; else $TMPDIR/amoeboid-<uid>/)
└── sockets, pid files, qemu arguments, ssh port; removed on exit
----

* Reset a VM: stop it and delete `~/.local/share/amoeboid/NAME`.
* Reclaim disk: old builds stay in the store until their `vm` link is replaced or deleted and you run `nix-collect-garbage`.

== Safety model

What protects your machine, and what doesn't.

Contained::
* The VM sees only the directories you share, plus your Nix store read-only.
* Read-only shares are enforced by the host-side file server.
* Files the VM creates, even as root, are owned by you; it can't create files owned by anyone else.
* Nothing the VM writes is read back by amoeboid. Its configuration is built only from host-side copies; the last run's shares are recorded host-side; the agent's copy of the configuration is never read.
* When amoeboid writes into the VM's directory (each start), it never follows symlinks the VM may have planted there.
* `amoeboid ssh` disables agent, X11 and credential forwarding regardless of your `~/.ssh/config`.
* `--detach` strips terminal control sequences from the console output it shows you.
* Rebooting from inside the VM only shuts it down; only you restart it.

Not contained::
* Anything in a read-write share can be modified or deleted by the agent.
* The VM's home (`.../NAME/guest/home`) is entirely the VM's. It may contain symlinks to anywhere on your machine; be careful when browsing, editing or copying from it on the host.
* ssh needs no credentials. The port listens on 127.0.0.1 only, but any local process can connect.
* The VM has outbound network access, including to services on your host's loopback (via `10.0.2.2`) and your LAN.
* The VM can fill your disk through its home or read-write shares.
* A configuration you adopt from the agent's copy runs with your privileges when the VM starts (see <<presets>>).

To require ssh keys instead: put a public key in the VM's `~/.ssh/authorized_keys` and set `services.openssh.settings.PermitEmptyPasswords = false;` in the VM's `recipe.nix`.

== Troubleshooting

`VM 'NAME' is already running`::
Connect with `amoeboid ssh --name NAME`, or stop it with `amoeboid stop --name NAME`.

`killing leftover virtiofsd-... from an earlier run`::
A previous launcher died without cleaning up; amoeboid cleaned up for you. Nothing to do.

`sshd didn't come up within ...`::
Read `~/.local/share/amoeboid/NAME/console.log`. First boots after big configuration changes can be slow; raise `--boot-timeout`.

`nix build failed`::
The build output above it names the problem, usually an error in the VM's `NAME/nix/recipe.nix`. Fix it there, or re-create the configuration with `--base-nix-config`.

`... is not a NixOS config dir (missing flake.nix)`::
`--base-nix-config` names neither a preset nor a configuration directory; the hint lists the presets.

`can't write .../guest/...: ... symlink`::
Something in the VM replaced a directory amoeboid writes to with a symlink. Inspect `~/.local/share/amoeboid/NAME/guest` and remove it.

`invalid configuration: ...`::
`run_config.kdl` has an unknown key or a bad value; every problem is listed. Fix the file, or delete it to have it recreated.

The console is the wrong size::
It is taken from your terminal at start. Fix it with `stty rows R cols C` inside, or use `amoeboid ssh`, which follows resizes.

The guest won't power off::
`amoeboid stop` kills qemu after `--timeout` seconds.

== How it works

. `start` copies a preset to `NAME/nix/` for a new VM, refreshes the guest copies, then runs `nix build path:NAME/nix` with the `host` input overridden by `host_<user>.nix`. The result links the microvm.nix qemu runner and virtiofsd.
. It writes, into the VM's state share, the mount table (`<tag> <rw|ro> <path>`, parents first), hostname, terminal size and ssh host key; and into the runtime dir, the extra qemu arguments: a user-mode network device with a `127.0.0.1:PORT -> 22` forward, plus one `vhost-user-fs-pci` device per share. Nothing that varies per start is part of the build.
. It starts one virtiofsd per share (the host store read-only, the state share, each `MOUNT`), as you, mapping the guest user's ids onto yours. Each is recorded in a pid file and cleaned up on exit, failure, Ctrl-C, SIGTERM or SIGHUP.
. It runs the microvm.nix runner, which reads the extra arguments, so devices attach without rebuilding.
. In the guest, a oneshot service sets the hostname, installs the host key and mounts the shares before the console login and sshd start.
. `stop` sends `system_powerdown` over the QMP socket, waits, then stops the helpers.

Fallible steps return `Result` values rather than raising; OS exceptions are converted at the edges with `attempt`.
